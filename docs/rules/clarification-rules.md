# Clarification And Decision Rules

## 证据顺序

需求或行为不明确时，按以下顺序寻找依据：

1. 当前用户明确指令与验收目标。
2. 相关代码、测试、构建配置和运行结果。
3. Workflow、knowledge、change、issue、ADR 和 Git 历史。
4. 官方文档、上游 issue/PR/commit 和协议规范。
5. 无法安全判断时再向用户询问最少的阻塞问题。

## 记录方式

- 已确认事实直接写入对应当前状态文档，并标注证据位置。
- 合理但未确认的推断写成 `[待确认]`，同时说明影响、候选方案和推荐，不得伪装成决策。
- 会影响范围、架构、数据、权限、安全、兼容或验收的问题才应阻塞实现；低风险细节沿用仓库既有模式并记录假设。
- 跨轮次仍未解决且影响交付的问题进入 `docs/issues/`，关键技术取舍进入 `docs/adr/`。
- 用户确认后，移除过时的 `[待确认]`，回写长期真相，并在 change 中留下决策时间和影响。

## 禁止事项

- 不仅凭 branch 名、旧 README、注释或产品品牌推断当前构建形态。
- 不把推荐方案写成“已确认”，不因赶进度跳过安全或数据完整性问题。
- 不重复询问能从仓库、工具输出或已给上下文得到的答案。
